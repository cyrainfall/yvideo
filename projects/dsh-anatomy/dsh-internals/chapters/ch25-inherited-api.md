# 第 25 章：Inherited API

## 核心思想

这一页覆盖的是 **harness 层之外、但每个插件都能看到**的那部分框架面：cordis core 加上 loader / hmr / timer 提供的 `ctx` 成员与事件。原文以速查表形式给出，逐条只有一行职责——所以本章的价值不在深度，而在**路由**：某件事该查哪一页、该订阅哪个事件、哪些条目属于固定的 vendor 源码。同时它是一个生成文件：手工修改会被 `pnpm run verify-cordis-catalog` 打回。

## 框架与方法

- **按源文件锚点分组读**
  - 何时用：不确定某个 `ctx` 成员归谁管、由谁提供时。
  - 怎么做：每条成员都带一个 `vendor/...` 源文件行号锚点。同一行里的条目共享一个锚点——`ctx.on` 与 `ctx.once` 都在 `events.ts:34`，`ctx.plugin` 与 `ctx.inject` 都在 `registry.ts:164`。先看锚点，再看详细页：Context / Fiber / Registry / Service 各有独立页面，事件分发方法在 `events.md`。

- **三层来源，读法不同**
  - 何时用：判断一条 API 的稳定性与依赖条件时。
  - 怎么做：
    - **cordis core**（`events.ts` / `registry.ts` / `fiber.ts` / `reflect.ts` / `context.ts`）：框架本体，前四章 API 参考讲的就是这一层。
    - **timer**（`vendor/timer/src/index.ts:4`）：`ctx.timer` 以及 `interval` / `timeout` / `throttle` / `debounce` 四个可撤销的定时器辅助。注意它的两种形态——`timer` 这个**键**是运行时提供的，四个 helper 则是**直接混入 `ctx`**（声明上用 `Pick` 表达）。
    - **loader**（`vendor/loader/src/index.ts`）：`ctx.loader` 是启动本应用的那个配置 Loader，**只在 loader 下存在**。

- **事件按标注分读**
  - 何时用：想介入框架内部流程时。
  - 怎么做：先看事件名后面有没有 `Waterfall:` 前缀——有前缀的四条（`internal/update`、`internal/config`、`internal/get`、`internal/set`）是链式分发，省略 `next()` 会改变行为；没有前缀的条目只有一行职责，未标注分发模式，不要假设它也是 waterfall。loader 侧的事件另有 `loader/` 前缀，`exit` 则是裸名。

- **标题里的三个来源与条目的对应**
  - 何时用：疑惑"hmr 相关的 API 在哪"时。
  - 怎么做：页头把来源写成 cordis core + loader / hmr / timer。条目里 loader 与 timer 都有显式归组（`loader/src/index.ts`、`timer/src/index.ts`），而热更新（hmr）的可观测面落在 `loader/*` 那组事件与 volatile 更新上——不另立一组。读的时候按"条目属于哪个源文件"归类，比按页头标题硬套更可靠。

- **一条条目值不值得依赖：三问**
  - 何时用：准备把某个 inherited 成员写进长期代码时。
  - 怎么做：一问提供者是谁——core 稳定、timer 运行时提供、loader 只在 loader 下；二问有没有 `Waterfall:` 标注——有标注意味着省略 `next()` 会改变行为；三问锚点行号对应的源文件是不是你能接受的耦合面。三问都过了再写。

- **生成文件的阅读纪律**
  - 何时用：想引用签名或类型时。
  - 怎么做：签名块用 `ts cordis-catalog` 围栏，围栏里是**原始源码的 JSDoc 紧跟方法声明**；`doc-typecheck` 会跳过这些裸声明片段（它们不是可独立编译的代码），签名里的类型名链接到文档该类型的页面。文件由 `scripts/gen-cordis-catalog.ts` 生成，由 `pnpm run verify-cordis-catalog`（`doc-sync` 的一部分）校验新鲜度。

## 关键概念

- **inherited（继承面）**：harness 自带 API 之下、由 vendor 源码固定提供的那层 `ctx` 成员与事件。
- **vendor 源码（vendored source）**：按 vendoring 政策固定在仓库 `vendor/` 下的框架代码，行号锚点指向它。
- **catalog 生成**：由 `gen-cordis-catalog.ts` 从源码抽取签名与 JSDoc 的过程。
- **`ts cordis-catalog` 围栏**：catalog 签名块的标识，`doc-typecheck` 据此跳过。
- **ambient handle（环境句柄）**：`ctx[Context.root]`、`ctx.fiber`、`ctx.registry`、`ctx.reflect`、`ctx.events`、`ctx.logger`，直接通向运行中的上下文图。
- **`ctx.loader`**：启动应用的配置 Loader，仅在 loader 下存在。
- **volatile config（易变配置）**：提交进运行中 fiber、不触发重挂载的配置值。
- **partial dispose（部分卸载）**：重载时某个配置条目被部分释放的过程。
- **patch context（补丁上下文）**：重载期间对上下文打补丁的时机。

## 心智模型

- 把这一页看成**索引而不是手册**：每条只够判断"是不是我要的"，细节去它链接的那一页。
- 当不确定一条 API 的依赖条件时，看它的源文件锚点：`loader/` 开头的需要 loader，`timer` 的在运行时才提供。
- 把 `internal/*` 看成框架自己的仪表读数，而不是对外扩展点——读它来观测，别靠它来构建业务。
- 把 volatile 更新看成"就地换值、不重挂载"：配置变了，实例还在。

## 反模式

- **手工编辑这个生成文件**：`verify-cordis-catalog` 会判定不新鲜，`doc-sync` 失败。
- **把 `internal/*` 当稳定公共 API 依赖**：它们是框架生命周期钩子，是给你观测和有限介入用的。
- **以为 `internal/update` 省略 `next()` 等于"更新失败"**：语义是**保留当前实例**，功能照常、只是没换实现。
- **假设 `ctx.loader` 到处都有**：只在 loader 下存在，别的运行方式里拿不到。
- **去 `ctx.timer.interval` 上找辅助函数**：四个 helper 已直接混入 `ctx`（`Pick` 声明），`timer` 键是运行时提供的那个。
- **把 `loader/volatile-update` 当广播**：它只派发给**所属 fiber**。
- **从这一页推时序**：原文给的是单行职责，不含触发顺序与前置条件。

## 实例演练

任务：为一个插件加上"上下线可见、配置改动不重挂载也能感知"的观测。按这一页做选型，而不是凭直觉。

1. **想知道某个插件实例什么时候被创建**：订阅 `internal/plugin`。它说的是"fiber 被创建"，不是"加载成功"——所以不能只靠它判断可用性。
2. **想知道它何时真正可用、何时卸载**：订阅 `internal/status`。状态每次转换都会发出，这是唯一给出"生命周期变了"的地方。
3. **想观测某个服务被读写的瞬间**：`internal/get` 与 `internal/set`，两者都是 `Waterfall`，意味着你的监听器可以介入解析过程；但正因为可以介入，写错就会影响所有读取者。
4. **想让配置改动落盘但不重建实例**：走易变更新路径——`loader/volatile-update` 把值就地提交进运行中的 fiber，且**只派发给所属 fiber**；配套的 `internal/commit` 负责持久化原始配置，`noSave` 为真时跳过。
5. **想改配置并让它真正生效**：`internal/config` 先解析候选（注入已激活后才跑，且不发布），再经 `internal/update` 应用。省略 `next()` 的语义是**保留当前实例**——所以"监听器写了一堆但实例没换"不是 bug，是契约。
6. **想介入热更新过程**：`loader/config-update` 表示配置树变了，`loader/entry-init` 表示某条目开始初始化，`loader/patch-context` 表示上下文正在被补丁，`loader/partial-dispose` 表示某条目被部分释放。四者各管一个阶段，**原文只给职责不给顺序**，所以不要在这一页上推时序，需要顺序时去读实际调用点。
7. **想在进程退出时收尾**：订阅 `exit`，它是"因信号退出"的时刻。

这个演练的结论是：这一页能让你在几分钟内选对事件，但不能让你理解时序。前者正是它的设计目标——"summarized tersely so the harness pages stay focused on repository-owned vocabulary"：把 vendor 面的速查留给它，把仓库自有词汇留给别的页。

## 关键要点

1. 这一页覆盖 harness 层之外的框架面：cordis core + loader / hmr / timer。
2. 先看源文件锚点判断依赖条件：`loader/` 需要 loader，`timer` 运行时才提供。
3. `ctx.timer` 的键是运行时提供的，四个 helper 已直接混入 `ctx`。
4. 只有带 `Waterfall:` 标注的四条 `internal/*` 事件是链式分发，省略 `next()` 会改变行为。
5. `internal/update` 省略 `next()` = 保留当前实例，不是更新失败。
6. `loader/volatile-update` 只派发给所属 fiber，不是广播。
7. 这是生成文件；要改内容就改源或改生成器，不要手改。
