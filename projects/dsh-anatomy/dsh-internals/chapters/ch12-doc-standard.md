# 第 12 章：文档规范

## 核心思想

`docs/AGENTS.md` 把「文档该长什么样」变成了可判定的工程规则：每个事实只允许一个家（tier），文档的范围由它的主题与树位置固定，篇幅由 manifest 里的数字兜底。所以写作的顺序不是先动笔再删，而是先定位、再定量、最后才写。

## 框架与方法

- **一个事实一个家（one home per fact）**：每一层有且只有一项职责，事实写在其所属层，其余位置只留链接。
  - 何时用：任何一次新增段落、新增小节、新增文档时。
  - 怎么做：先问「这个事实的可查范围是什么」，再取分层表的对应行。表里的「不属于此层」一列就是判据：如果这段内容属于别的层，无论它写得多好都要搬走。

- **范围由主题与树位置固定（subject and tree position fix scope）**：文档以自己的主题为范围，对直接子级只写到用途、职责与高层行为，更细的细节链接到拥有它的后代。文档类型不会扩大这个范围；一份 reference 只对自己的主题可以穷尽。
  - 何时用：一段话开始解释「下游是怎么实现的」时。
  - 怎么做：把这段降级成一句链接。Testing mechanisms、fixtures 与 harnesses 放在最低的拥有层，上层只链接过去。postmortem 是事件范围的 reference，其中的时间顺序记录的是证据，不是教学顺序。

- **tutorial 与 reference 二选一**：范围内每份文档都要被归类。tutorial 沿有序路径走向一个结果，只引入该步骤需要的东西；reference 定义查找范围与当前行为，不设教学顺序。
  - 何时用：起草文档前，以及一份文档同时承担两种角色的迹象出现时（前半讲概念、后半讲参数）。
  - 怎么做：把两者实质性的内容分开；任一方较小时，给该节打标签而不是默认混排。写 tutorial 之前，私下给读者的起点知识定级，并给每个概念标成 beginner / intermediate / advanced；先建立前置再引入依赖概念，难度渐进上升，把不必要的进阶材料移到后面的 tutorial 或 reference。

- **作者顺序（author in this order）**：定位文档在树中的位置 → 设定它被允许的细节层级 → 选 tutorial 或 reference → 给 tutorial 按前置与难度排序 → 把属于后代的细节搬走 → 用链接替换低层解释。
  - 何时用：写作卡住时，作为回归检查表。
  - 怎么做：六步按顺序走完再写第一句；跳步的典型后果是写了一半才发现整节都属于别的层。

- **文档预算（wordcount budgets）**：`scripts/doc-budgets.manifest.json` 设定常驻文档的上限，`pnpm run verify-doc-budgets` 拒绝超额或缺文件的条目。
  - 何时用：`verify-doc-budgets` 变红。
  - 怎么做：按 Relocate → Condense → Raise 三级处理。先把属于别的层的内容搬走，需要时留一行链接；再把该留在这里但可以更短的内容压缩；最后才抬上限，且必须在 PR 里解释这次 manifest diff。上限设得太低本身就是一个 budget bug。
  - 附加规则：ceiling 是护栏而不是缩减目标。等于或低于目标时保留至少 5% 余量；高于目标时冻结上限，直到搬家或压缩把文档带回目标以下；只有文档确实还有余量时才降上限。

- **成对更新（pairs update together）**：中英对照页按术语引导、单遍、由活跃 agent 完成：重排首次出现的注解位置、保留未被触及的 prose、再重新记录；`dsh-translate-docs` 保持由用户主动调用。
  - 何时用：改动任一语言的正文时。
  - 怎么做：把中文页看成生成物的镜像——只改影子等于没有改；改动落在同一变更里，并遵守 i18n 契约的范围与排除项。

- **生成参考不得手改（generated reference）**：per-page 的 `cordis-surface` 区块、`cordis-api/context.md`、`tool-catalog`、`config-catalog`、`persistence-catalog`、`module-graph.md`、`cli-help` 的英文源都由源码再生成并受 freshness gate 约束，中文对照只走 pairing workflow。
  - 何时用：发现某些表格「看起来该补一行」时。
  - 怎么做：改生成器或改源码，然后重新生成；手工编辑生成的英文源或区块会越过 freshness 校验。

- **slop 清单（the slop checklist）**：九个猎杀项，`dsh-doc-writing` 把它当作审计列表跑。
  - 何时用：交稿前与 review 时。
  - 怎么做：逐项搜证——重复规则（搜一个有辨识度的短语，只留一个家）、跨层历史、实现状态标注（"implemented!"、"future: …"）、手工重述的目录与测试/包清单、推理过程记录（逐步实现叙述、显然分支的证明、测试走查、被否掉的局部方案）、在兄弟方法旁重复的理由、段落墙（一段塞多条规则加括号补充）、强调膨胀（满篇 bold 与 "critically" 等于没有重点）、`implemented/` 笔记里的 spec-speak（"should"、迁移计划、验收清单）。

## 关键概念

- **tier**：事实的归属层，一层的职责由分层表定义，一层的「不属于此层」同样是规则。
- **standing order**：root `AGENTS.md` 承载的常驻指令——每次会话都需要在上下文里、一到三行、并链接到它的家。
- **tutorial**：沿有序路径走向结果的文档，只引入当前步骤所需的概念。
- **reference**：定义查找范围与当前行为、不设教学顺序的文档。
- **Agent Note**：活跃的决策记录，写清 why、放弃了什么、需要什么验证；`implemented/` 用现在时描述已上线的现实；archived 笔记是冻结的历史，永不作为当前权威。
- **postmortem**：事件故事的层，也是唯一允许战史叙事的层。
- **生成参考（generated reference）**：英文源由源码再生成、受 freshness 门控的页面；中文对照按配对流程更新。
- **headroom**：上限之下预留的余量，规范要求至少 5%。

## 心智模型

- 当一段文字想回答「为什么是这样」时，把它看成 Agent Note 的候选而不是 `architecture.md` 的段落。
- 把 root `AGENTS.md` 看成常驻内存：任何超过一到三行的东西都在偷上下文预算。
- 当 review 里出现「已实现！」这类状态标注时，把它看成一个会腐烂的时间戳——删掉，让仓库布局与包 manifest 说话。
- 把中文对照页看成一个投影：它不能独立成立，只反映英文源与源码的当前状态。

## 反模式

- **同一规则写两处**：两处迟早不一致，且读者无法判断哪处权威；搜一个有辨识度的短语，只留一个家。
- **历史写进当前文档**：当前文档应陈述现在的事实，历史属于 commit、PR、Agent Note、postmortem 或有范围的持久化记录。
- **实现状态标注**：状态会腐烂；仓库布局和包 manifest 才是状态的载体。
- **手工重述目录与清单**：源码或生成器是权威时，重述只会漂移。
- **推理过程记录**：保留结论性契约或持久理由，删掉推导路径本身。
- **在兄弟方法旁重复理由**：理由应写在拥有的能力或辅助函数处一次。
- **段落墙**：一段承载多条规则加括号补充，读者无法把它拆成可执行项。
- **强调膨胀**：满篇 bold、CAPS、"critically"，真正改变行为的那个从句反而消失。
- **`implemented/` 里写 spec-speak**：已实现的笔记应该描述「是什么」。

## 代码/配置示例

预算门控就是一行命令，红绿即结论：

```sh
pnpm run verify-doc-budgets
```

围栏语言的三种标注，含义不同，都不能随手写：

```text
 ts            → 必须能编译（doc-typecheck 校验）

```

## 实例演练

`verify-doc-budgets` 报某份文档超额，走一遍三级处理。

第一级 Relocate。逐段问「这个事实的家在哪」。典型发现：一段写明暗主题覆盖的文字，其实属于主题包的 reference；一段解释为什么这样设计，属于 Agent Note；一段讲怎么验证，属于 cookbook。搬走之后在原处留一行链接——链接不是内容，不占预算。

第二级 Condense。剩下确实属于本文的内容里，常见问题是段落墙：一段同时说了「宽度变小时先保留语义组」和「高度增加时明确哪个区域伸展」。拆成两条独立规则，去掉括号里的补充说明，长度下降而可执行性上升。注意上限是护栏不是目标：即使压到线以下，也要留至少 5% 余量，否则下一次正常编辑又会红。

第三级 Raise。只有当内容既属于这里、又已经无法再短时才动 manifest，并在 PR 里解释这次 diff。如果这次改动后文档只是刚好压线，正确做法是冻结当前上限，直到后续搬家或压缩把文档带回目标以下；反过来，只有文档确实还有余量时才降上限——降到一个刚好够用的数字，等于把下一次编辑的成本预支给后来的人。

最后一步是 slop 复查。超额通常不是「话太多」，而是「写错地方」：手工重述的清单、跨层历史、实现状态标注都会同时制造超预算和审查负债。把它们清掉，比逐字删减更有效。

## 关键要点

1. 动笔前先定位：事实属于哪一层，决定了它能不能写在这里。
2. 文档的类型不会扩大它的范围；reference 只对自己的主题可以穷尽。
3. 写 tutorial 前先给读者与概念定级，前置先于依赖。
4. 预算红了按 Relocate → Condense → Raise 走，抬上限必须在 PR 里解释。
5. `ts` 围栏必须能编译；`type-equiv` 与 `public-api` 要在 manifest 登记，否则是永久漂移。
6. 改文档时同一次变更里更新拥有的 subsystems 页与中英对照。
7. 引用当前文件用相对 Markdown 链接，历史引用用 tag 或 PR 号。
