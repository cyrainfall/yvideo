# 第 40 章：评审与贡献

## 核心思想

评审不是「读一遍 diff 表示同意」，而是一组有判据、有证据、有归属的动作：每条意见要落到引入它的那一层，每条结论要能指出违反了哪个关系，每条持久化变更要留下双语记录，每次改写推送后要重新读取状态。本章的四套流程分别守住四个面——堆叠链的归属、持久化历史的兼容、界面关系的可见性、以及评审知识本身的演进。

## 框架与方法

- **堆叠 PR 的五条基本规则**：先把归属搞清楚再动手。
  - 何时用：评审意见同时落在一条 `A ← B ← C` 依赖链的多个 PR 上。
  - 怎么做：①每个 PR 分支一个 worktree，并行修复绝不共享同一个 checkout；②GitHub 的 stack 对象是权威依据——base 分支确定预期顺序，`PullRequest.stack` 与 `stackEntry.position` 证明 GitHub 已识别该堆叠，不得仅凭分支链吻合就当成官方堆叠；③修复落在**引入问题**的那个 PR 上再沿堆叠向上流动（评论针对 `B` 引入的代码就在 `B` 修，再把 `B` 的变更传播到 `C`，哪怕 `C` 也含该文件）；④每项评审修复保留为独立 commit，后续 rebase 可能改 OID，但不得 amend 掉已评审的修复，只有自己尚未推送且尚未评审的工作才可 amend；⑤以启用 rerere 的 rebase 传播，改写历史的推送必须受 lease 保护，禁止直接 `--force`。

- **沿堆叠解决意见的七步**：先验证，再映射，再传播。
  - 何时用：开始处理一批跨层评论。
  - 怎么做：①对照代码就事论事验证每条评论——评审者可能指出了正确的症状却误诊了原因；②把接受的发现映射到引入它的 PR；③按顺序传播到每个受影响的子 PR；④委派的修复要「信任但验证」，亲自在实际代码树上重跑门禁；⑤在评审线程里回复（replies API）而非发顶层评论，说明修复内容与承载它的 commit 或 head；⑥每次改写推送后重读未解决线程、批准状态、可合并性与检查结果；⑦只通过官方堆叠流程落地。

- **回归守卫必须能变红**：证明守卫有效的方式是让它失败一次。
  - 何时用：新增或修改一个回归守卫。
  - 怎么做：引入回归 → 观察它变红 → 还原。两种情况都通过的守卫什么也守不住。subagent 把问题重新定性为「已处理」时，这是需要亲自深入的信号——它的报告描述的是意图，不一定是实际落地的内容。

- **持久化类型变更的三步**：预览 → 记录 → 检查提交推送。
  - 何时用：改了会话持久化类型声明。
  - 怎么做：①`pnpm --silent run verify-persistence-changes --json` 预览（必须加 `--silent`，否则 pnpm 会把生命周期失败文本追加到 stdout）；②写一份含 `en` 与 `zh` 的本地 JSON，两者各含 `summary`、`compatibility`、`verification` 字符串，再 `pnpm --silent run persistence-changes --record <日期-短名> --prose <path> --json`；③`pnpm run doc-sync`，然后正常提交推送。被引用类型可能影响多个事件摘要，要检查每个受影响的根；历史覆盖新 schema 之前验证会失败。

- **同版本还是升版本：显式决策**：结构差异本身不足以要求更高写入器版本。
  - 何时用：记录被标为 `requiresCompatibilityReview` 的变更。
  - 怎么做：在记录的兼容性部分说明**两个读取方向**的读取器行为，在验证部分记录已执行的检查。证据支持保持版本时提供 `--decision same-version`；若有效判别信息无法阻止不安全解释，则走添加格式版本流程并选 `--decision version-bump`，且该记录必须包含自身的 `SessionHeader.version` 递增转换。头版本未变却缺显式决策，会以 `decision-required` 失败。

- **UI 设计审查的判断优先级**：先结构，后细节。
  - 何时用：明确要求的完整审查，或改动影响面足够大的回归检查。
  - 怎么做：先检查对齐与空间分组，再审查密度、层级、状态、组件选型、图标光学与几何。对齐先核对图标完整空间（含有意保留的内部留白）、文字列与间距，再检查实际轮廓——热区不等于图标框，不逐个拉齐 glyph 的像素边缘。关联图标与文字按同前景色规则核对，覆盖明暗主题的实际颜色与透明度。

- **按视觉影响选范围**：文件数量和包边界不能决定检查范围。
  - 何时用：决定这次要看到多少。
  - 怎么做：局部文案／图标／颜色／间距先看所属页面或弹窗上下文，并检查所属组、相邻组及共用轴线或角色的受影响并列元素；页面、表单或卡片布局改动把所属页面当整体审查；共享组件要排查全部受影响使用方，并在实际组合上下文中检查每种布局、内容与状态变体；全局字体、令牌或样式要按组件族与页面布局扩大覆盖。共享组件的证据只有在实现、尺寸、容器约束、内容行为和状态等价时才能复用。

- **dsh-code-review skill 的周期维护**：小周期 PR，而不是一次性审计。
  - 何时用：维护评审 skill 本身。
  - 怎么做：每日用 2 个 UTC 日的重叠窗口、每周用 7 日窗口跑包装脚本；工具按窗口挑选可从 `origin/master` 到达的合并 PR，收集合并前带 commit 锚点的人工评审反馈，与最终落地的 patch 比较，由两个独立配置的评审适配器分类，主适配器起草完整修订版，两个适配器评审同一 diff，直到双方批准，最后对候选项跑 `pnpm run doc-sync` 与 `pnpm run lint`。

## 关键概念

- **`stackEntry.position`**：GitHub 已识别堆叠的证明字段之一；缺它不是「大概也算」，而是不能上报为官方堆叠。
- **rerere**：`git config rerere.enabled true` 后 Git 复用已记录的冲突解决结果；暂存前必须检查每个复用的结果。
- **lease 保护**：改写历史推送的强制约束——远端 head 期间前移则中止，不得覆盖。
- **`requiresCompatibilityReview`**：变更被标记为需要显式兼容性评审的判据。
- **`decision-required`**：头版本未变、被标记的变更却缺显式决策时的失败码。
- **判断优先级（judgment order）**：对齐与空间分组 → 密度、层级、状态、组件选型、图标光学、几何。
- **`skipped-pulls.json`**：无法到达 `origin/master` 或超出 250 个 commit 获取上限的 PR 的记录处；跳过而不中止本次运行。
- **fail-closed**：某批次适配器响应未通过 schema 或 ID 校验时，整批标记为不明确而不是猜测。
- **提升 manifest（promotion manifest）**：把每条拟议规则映射到源反馈与已落地证据的清单；判定候选 diff 是否值得提升的依据。

## 心智模型

- 把堆叠链看成一条单向的因果流：修复必须落在源头，下游只是承接——在错误的那一层修，评审者就永远看不到修复。
- 把持久化记录看成「给未来读取器的说明书」：`summary` 说改了什么，`compatibility` 说两个方向还能不能读，`verification` 说你怎么证明的。
- 把 UI 发现写成关系句：不是「间距不对」，而是「标题到操作组的距离小于操作组内部距离，视觉上把标题粘到首个操作」。
- 把评审 skill 的候选 diff 看成提案而不是结论：评审者已批准不等于应当接受，最终决定在操作员。

## 反模式

- **因为「评审者已经批准」就直接接受候选**：维护者约定要求操作员按 diff 本身判断，检查清单是否膨胀、是否有历史叙述、是否据单次事件作无依据外推。
- **逐字提交适配器输出**：提升期内的小幅编辑（收紧措辞、移除只对源 PR 上下文有意义的示例、并入现有规则）是预期行为，也是这套工作流依赖的判断来源。
- **用 `gh stack sync` 后不再验证**：它可能先发布再校验，必须按 pre-push 检查在同步后立即验证。
- **在未修复的代码上跑一遍守卫就宣布有效**：两种情况都通过的守卫什么也守不住。
- **用 `--check` 冒充 base/head 评审**：`--check` 只比较当前源码与已确认历史，不能证明人类评审过这次变更。
- **只为「不同变更」复用同一份兼容性说明**：说明必须描述实际的新转换与已执行的检查。
- **把局部检查表述成整页结论**：不能给出的覆盖范围要明写，局部 fixture 不能替代整体中尚未检查的部分。

## 代码/配置示例

改写推送前先启用 rerere，暂存前检查复用结果：

```sh
git config rerere.enabled true
# 修复落在引入问题的层，再沿堆叠传播
gh stack rebase
# 逐层验证后再发布
gh stack push
```

## 参考表

堆叠修复的验证清单：

| # | 检查项 |
|---|---|
| 1 | 每个已修复 PR 的当前 diff 都在引入问题的那一层包含预期修正 |
| 2 | GraphQL 报告的官方堆叠只有一个且顺序符合预期 |
| 3 | 每个子 PR 相对于父 PR 的 diff 只显示该子 PR 自身的变更 |
| 4 | 每次改写推送后重新审计了未解决线程、批准状态、可合并性与检查结果 |
| 5 | 相关门禁在堆叠中每个受影响 PR 上都通过，而不仅是顶部 |
| 6 | 每一项评审修复仍是独立 commit，OID 变更但历史未被抹去 |

按视觉影响选择最小检查范围：

| 改动 | 最小检查范围 |
|---|---|
| 局部文案、图标、颜色或间距 | 所属页面／弹窗上下文；所属组、相邻组及共用轴线或角色的受影响并列元素 |
| 页面、表单或卡片布局；新页面或弹窗 | 所属页面或弹窗整体，含相关滚动与展开内容 |
| 共享组件 | 全部受影响使用方，并在实际组合上下文中检查每种布局、内容与状态变体 |
| 全局字体、令牌或样式 | 按受影响的组件族与页面布局扩大覆盖，不能当局部改动 |
| 无预期样式变化的行为改动 | 可能改变可见关系的状态：加载、错误、禁用、展开、焦点 |

审查记录的可选提示：

| 观察项 | 记录内容 | 示例 |
|---|---|---|
| 任务与分组 | 每组描述或操作什么，含哪些子组，与谁相邻 | 会话标题／三操作组；成员区／任务区 |
| 对齐 | 对象、轴线、参照容器及有意的例外 | 同类行文字起点由基线定义；主按钮内 icon 与文字整体居中 |
| 间距 | 哪些是组内、重复单元之间和组间距离 | 标题与所属卡片比与前一个分区更近 |
| 并列几何 | 可比较角色的可见尺寸、圆角与颜色关系 | 圆形底板等大；搜索提示共用一个前景色角色 |
| 状态 | 同时叠加及相邻共存的组合 | 当前会话选中，同时另一条会话悬停 |
| 证据范围 | 能看到什么，哪些尚未检查 | 完整侧栏与隔离会话行的区别 |

评审 skill 候选的三种处置：

| 处置 | 做法 | 约束 |
|---|---|---|
| 丢弃 | 删除保存的候选版本 | 下次运行会依据届时的当前 skill 重新考虑同一份反馈 |
| 留待成批 | 与后续版本合并处理 | 源 skill 检查仍适用；`master` 先变则重跑分析或手动 rebase 并重新评审 |
| 提升 | 在干净 `master` checkout 跑提升辅助工具 | 会校验当前 skill 与记录的源 blob 一致；漂移则停止而不覆盖 |

## 实例演练

评审意见落在一条三层堆叠的中间层，走一遍完整链路。

runner 先做归属判断。评论在 PR `B` 上指出一个越界下标，而真正引入该下标的是 `B` 的重构，`C` 只是继承了同一文件。因此修复必须在 `B` 上做——在 `C` 上修，`B` 会带着 bug 交付，`B` 的评审者也永远看不到修复。

动手前先启用 `git config rerere.enabled true`，并给 `B` 开自己的 worktree。修复作为一个独立 commit 落在 `B`，不使用 amend——`B` 上已有的 commit 是别人评审过的。

传播用 `gh stack rebase`，逐个验证被改写的层，再 `gh stack push`（受 lease 保护）。如果 `C` 上也有同样文件且冲突，rerere 会复用已记录的解决结果；暂存前逐个检查，不能盲信。

接着是验证闭环。委派的修复要亲自在实际代码树上重跑门禁；如果这次同时加了一个回归守卫，就按「引入回归 → 观察变红 → 还原」证明它真的会红。

然后是沟通。在原来那条评论下用 replies API 回复，说明修了什么、当前由哪个 commit 或 head 承载——不要发顶层评论，那会让后续读者失去上下文。

最后是重读。改写推送会改变 commit OID，也会让部分内联锚点过期，所以未解决线程、批准状态、可合并性与检查结果都要重新审计一遍；「OID 变了但评论还显示 resolved」不足以证明问题当前仍处于解决状态。

结束时核对验证清单：官方堆叠只有一个、每个子 PR 相对父分支的 diff 只含自身变更、受影响的三层门禁都过。

## 关键要点

1. 修复落在引入问题的那一层，再沿堆叠向上传播；在错误层级修等于对上游评审者隐藏问题。
2. 每项评审修复一个独立 commit；只有自己未推送、未评审的工作才可 amend。
3. 改写推送用 rerere 加速并检查复用结果，全程受 lease 保护，不用 `--force`。
4. 改写后必须重读未解决线程、批准、可合并性与检查——OID 变化会使旧状态失效。
5. 持久化变更要双语、三字段、显式决策；结构差异不自动等于升版本，头部递增才可推断 `version-bump`。
6. UI 发现要写成可观察的关系，并且范围由视觉影响而不是文件数决定。
7. 共享组件证据只在实现、尺寸、容器约束、内容行为与状态等价时可复用。
8. 评审 skill 的候选 diff 由操作员按 diff 判断，可以丢弃、留待成批或提升；不要逐字提交适配器输出。
