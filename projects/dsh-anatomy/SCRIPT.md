## Frame 1 — 两百个插件的秩序

上一季，我们把这台机器拆过一遍。
拆到最后，剩下一件事：它没有内核。
没有内核，一切只能靠插件。
这台机器的配置目录里，条目有两百四十八条。
两百四十八条，没有缠成一团意大利面。
答案不在插件里，在插件之间。
生成的能力表里，一百二十一个能力，六十四条是核心。
只有三十六条，是可替换的接缝。

## Frame 2 — 一个能力，三个位置

先只看一个能力。
它在这个仓库里占三个位置。
第一个位置是定义：包叫 D S H shell，它拥有 C T X 点 shell 这个键。
第二个位置是提供方：这台机器装的是 Bash 的两个，本地执行器和沙箱执行器。
第三个位置是消费方：把 bash 交给模型的工具，还有给 Windows 用的 P W S H。
定义在上，提供方和消费方分在两边，中间不画箭头。
消费方连的是那条线，不是某个人。
三个位置齐了，才算一个能力。

## Frame 3 — 定义是类，不是一个名字

先说定义：Service Definition（服务定义），它是类，不是一个名字。
它有两半：一半把 shell 写进 Context，类型是 Shell 执行器。
另一半是一个抽象类：Shell 执行器继承 Service。
抽象类才有构造，构造里调一下 super，shell 这个键就是在那里交出去的。
位置是被一个类占住的，不是一个字符串。
一个上下文，这个位置只容一个实现。
第二个实现装载进来，直接抛错：service "shell" has been registered。
这不是 shell 包的守卫，是 C O R D I S 的规矩：一个服务名只能占一个位。

## Frame 4 — 提供方是继承，不是重写

再说提供方：这台机器装的是 bash-local 和 bash-sandbox。
本地那个继承的是 Shell 执行器。
沙箱那个继承的是 Local Bash 执行器，不是抽象类。
所以它不是重写一遍，是继承一份，再改。
改的是执行世界，不是工具契约。
沙箱那个多要两个缝：inject 里写着 sub process、sandbox、sandbox policy。
本地那个只注入 sub process。
换提供方，连带换的是依赖面，消费方一个字不用改。

## Frame 5 — 消费方只认 key

最后是消费方：只认键，不认人。
工具 bash 只认 shell：读 sandbox mode，调 execute。
整个工具层，没有出现过任何一个执行器的类名。
它把 shell 写进 inject：加载时就要，缺了就不启动。
依赖表更直白：定义包 D S H shell 只在 peer 里，运行期依赖只有一个。
两个提供方都不在运行期依赖里；bash-local 只在 dev dependencies，给测试用。
缺席也分两种。
硬依赖缺席，插件停在 pending；写 C T X 点 get 的那条缺席，才走到 unavailable。

## Frame 6 — 五种挂法，选错要重写

同样是把能力挂上去，有五种形态。
命名注册表，C T X 点 llm：多个提供方并列，各占一个名字，只拒绝重名。
单槽，C T X 点 browser use：只存一个，第二次注册无条件抛错。
有序尝试，认证链——传输层的缝：按注册顺序问，第一个给出存活 Peer 的就赢。
每上下文一实例，C T X 点 shell：没有注册表，只有一个名额。
注册即绑定，C T X 点 credentials：插件名就是凭据作用域的键。
形态在发布时就定了。
选错，消费方要全部重写，这一条是判断，不是仓库里写着的。

两边都合法，选哪边是设计。
