## Frame 1 — 从哪下手

前五集，我们把这台机器拆了一遍。
知道它没有内核，知道一切是插件，知道一轮对话怎么走，也知道模型的手怎么动。
现在换个方向。
不是拆，是装。
我想加一个自己的东西，从哪下手。
答案比想的轻：加一个包。
包里可以往三个地方伸手：模型、人、界面。
不用改内核。内核本来就没有。

## Frame 2 — 三个入口

第一个入口，面向模型：工具。
和第二集那个玩具不同，这次是真身。
ctx.tools.register，交三样东西：一个名字，一份 JSON Schema，一个 execute。
下一步请求，模型的菜单里就多了一项。
第二个入口，面向人：命令。
ctx.commands.register，一条斜杠命令，一个 handler。
handler 收到你打的字，直接返回一段给界面看的话。

## Frame 3 — 两种产物

工具和命令像，但归宿不同。
工具跑完之后，是 tool result 这一条：进日志，也进模型可见的历史。
命令跑完是 command run 和 command done，成对写进同一本日志。
但它是 log-only。
也就是说，命令和它的回执，永远不进模型的历史。
你可以用命令做事，而不污染对话。
命令也分层：全局的，和挂在某个 agent 名下的，近的盖住远的。
和第五集的工具，同一套规矩。

## Frame 4 — 界面留的空位

第三个入口，面向界面。
一个包可以带一个浏览器半边：package.json 里写 dsh.client，指向 ./client。
它不改页面的根，只往一个 slot 里放东西。
slot 是界面提前留好的空位，比如输入框下面那一层。
加载一个包，只注册一个工厂，什么都不渲染。
真正挂上去，是两句话：ctx.slots.inject 找到那个空位，ctx.slots.register 交一个组件。
还要交一个 id，一个顺序。id 是你的位置，顺序决定你排在谁前后。

## Frame 5 — 一个包

三个入口合起来，是一个包。
package.json 说它是什么：名字、导出、patch 在哪一边。
cordis.patch.yml 说它往树里插哪一条：一个 id，一个包名。
所以安装，其实是第三集那件事再走一遍。
包进 node modules，patch 插一条，树再长出来，那一条的插件开始 apply。
界面上的动作，是插件页里的添加插件；模型这边，是 plugin_manager 的 install bundle。

## Frame 6 — 真装一次

真装一次。
给第二集那个 greet，补上命令和面板，装进去。
install bundle 返回 application: applied。
applied 的意思是：已经活了，不用重启。
插件的条目出现了，模型的工具清单里多了一个 greet，输入框下面多了一个点。
这就是热更新的边界。
能替换的时候，装包、卸包、改配置、换代码，都是活的。
但有五种情况会退回下次启动：没有 hmr；包换了目录；改动碰到了进程自己加载的模块；插件跑在列表外面；或者比不出模块的差异。
浏览器那边更简单：页面跟着 Host 的模块图走，装一个卸一个，不用刷新。

## Frame 7 — 卸下来

然后卸掉。
remove bundle，也是 applied。
条目没了，工具没了，那个点也没了。
第二集说过，注册是可逆副作用。
到这一集，这句话有了完整的样子：一个包进来，树多一个节点；一个包出去，树少一个节点，界面自己收拾干净。
五集拆，一集装。
这台机器没有内核，所以它可以变成任何形状。
接下来，轮到你了。
